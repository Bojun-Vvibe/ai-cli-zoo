## What it is

`wrangler` is Cloudflare's official CLI for building, previewing, and
deploying code that runs on the Cloudflare Workers edge runtime — a
V8-isolate-based serverless platform that executes JavaScript, TypeScript,
WebAssembly, and (via the `python-workers` runtime) Python on Cloudflare's
~300+ PoPs. The same binary also drives Cloudflare Pages, R2 object
storage, KV, D1 (SQLite-at-the-edge), Durable Objects, Queues, Hyperdrive,
Vectorize, and the AI Gateway / Workers AI bindings — i.e., the whole
Cloudflare developer-platform surface.

## Why it's interesting

- **Local dev that actually runs the production runtime.** `wrangler dev`
  boots [`workerd`](https://github.com/cloudflare/workerd), the same open-source
  V8-isolate runtime Cloudflare runs in production, so your local
  iteration matches deploy semantics down to the `Request`/`Response` and
  binding behaviour. No "works locally, breaks in prod" gap.
- **Bindings declared in `wrangler.toml`, injected as typed objects.** KV
  namespaces, R2 buckets, D1 databases, Queues, Durable Objects, secrets,
  and AI models all show up as `env.MYBINDING` with TypeScript types
  generated by `wrangler types`. The same file is the deploy manifest.
- **Edge-native primitives in one CLI.** `wrangler r2 object put`,
  `wrangler d1 execute`, `wrangler kv key put`, `wrangler queues consumer
  add`, `wrangler vectorize insert`, `wrangler ai run` — every Cloudflare
  data/AI service has a first-class subcommand, so scripting against the
  whole stack does not need a separate Terraform run.
- **`wrangler tail` for live edge logs** streams structured logs from a
  deployed Worker globally with filtering by status / sampling rate /
  IP — much faster feedback loop than chasing logs through the dashboard.
- **`wrangler deploy --dry-run --outdir`** writes the bundled, minified
  Worker to disk, which makes it trivial to feed into a separate
  CI-controlled deploy step or a `cf-pages` / `wrangler-action` pipeline.

## Install

```bash
# npm (recommended — pinned per-project)
npm install --save-dev wrangler@4

# pnpm / yarn / bun all work
pnpm add -D wrangler@4

# global (ad-hoc)
npm install -g wrangler

# verify
npx wrangler --version    # 4.87.0
npx wrangler login
```

## Examples

```bash
# scaffold a new Worker
npm create cloudflare@latest -- my-worker

# local dev against the production runtime, hot-reload
npx wrangler dev

# deploy to *.workers.dev (or your zone, if configured)
npx wrangler deploy

# inspect / mutate edge data services
npx wrangler kv namespace create SESSIONS
npx wrangler kv key put --binding=SESSIONS abc123 '{"u":42}'
npx wrangler r2 bucket create uploads
npx wrangler r2 object put uploads/hello.txt --file=./hello.txt
npx wrangler d1 create app-db
npx wrangler d1 execute app-db --command "SELECT 1"

# tail live edge logs from the deployed Worker
npx wrangler tail --format pretty --status error

# build only, no deploy — feed bundle into your own pipeline
npx wrangler deploy --dry-run --outdir=./dist
```

## Use when

- You want true edge-runtime serverless with sub-millisecond cold start
  and per-request billing, reaching every Cloudflare PoP without
  region selection.
- The app is naturally request/response shaped (APIs, middleware, image
  resizing, A/B at the edge, auth gateways, RAG retrieval) and benefits
  from being co-located with R2 / KV / D1 / Vectorize at the edge.
- You want one CLI to drive Workers, Pages, R2, D1, KV, Queues, Durable
  Objects, AI, and Vectorize — instead of stitching `aws` / `gcloud` /
  `az` calls together.

## Use something else when

- You need long-running stateful processes, raw TCP/UDP sockets beyond
  what Workers offers, or multi-GB RAM single instances. A microVM PaaS
  like [`flyctl`](../flyctl/) or a real container platform is a better
  fit.
- You need to run arbitrary native binaries, run a database server, or
  use `fork()` / threads / filesystem semantics — V8 isolates do not
  provide these.
- You want full IaC control / multi-cloud portability — Terraform or
  Pulumi targeting Cloudflare's API gives you state files and drift
  detection that `wrangler.toml` alone does not.

## Alternatives

- [`flyctl`](../flyctl/) — Firecracker microVMs with global Anycast,
  better fit for long-running and stateful workloads.
- `vercel` CLI, `netlify` CLI, AWS `sam` / Lambda CLIs — competing
  serverless deploy tools with different runtimes and pricing.
- Cloudflare Terraform provider — if you prefer declarative IaC over the
  `wrangler deploy` flow.
