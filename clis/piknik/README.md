# piknik

> **A copy/paste-over-the-network daemon: a tiny
> Go server (`piknik -server`) acts as a relay,
> and the same binary on every other machine sends
> (`piknik -copy`) or receives (`piknik -paste`)
> clipboard payloads via authenticated, encrypted
> HTTP**. Run `tar c logs/ | piknik -copy` on a
> remote box, then `piknik -paste | tar x` on your
> laptop and the bytes arrive — no `scp`, no
> `rsync`, no opening reverse SSH tunnels, and the
> relay never sees the plaintext (HMAC + symmetric
> encryption client-side). Pinned to **0.10.2**
> ([LICENSE](https://github.com/jedisct1/piknik/blob/master/LICENSE),
> ISC / BSD-2-Clause).

Source: <https://github.com/jedisct1/piknik>

## TL;DR

`pbcopy` / `xclip` / `wl-copy` solve "clipboard on
*this* machine"; `magic-wormhole` / `croc` solve
"one-shot file transfer between two humans"; SSH
agent forwarding solves "I trust this hop". None of
them solves "I'm bouncing between five remote
shells all day, and I want a single shared
clipboard so `piknik -copy` on the bastion shows up
on my laptop on the next `piknik -paste`". `piknik`
is purpose-built for that workflow: a long-running
relay (a few KB of RAM, one HTTP port) plus the
same binary in client mode on every endpoint, with
shared keys generated by `piknik -genkeys`. The
relay is dumb on purpose — it just buffers an
encrypted blob keyed by HMAC; it can run on a
$3/month VPS or anywhere with a public IP and the
contents stay private to whoever holds the keys.

## Install

```bash
# Homebrew (macOS / Linuxbrew)
brew install piknik

# Go install (any platform with Go ≥ 1.20)
go install github.com/jedisct1/piknik@0.10.2

# Pre-built tarball (release page)
curl -LO https://github.com/jedisct1/piknik/releases/download/0.10.2/piknik-linux_x86_64-0.10.2.tar.gz
tar xzf piknik-linux_x86_64-0.10.2.tar.gz
sudo install linux-x86_64/piknik /usr/local/bin/

# Generate a key set (do this ONCE, then copy the config to every machine)
piknik -genkeys > ~/.piknik.toml
# Edit ~/.piknik.toml: set Connect = "https://relay.example.com:8075"
#                     and Listen = "0.0.0.0:8075"  (only on the relay)

# verify
piknik -version    # piknik 0.10.2
```

The same binary is server, sender, and receiver —
the difference is just the flag (`-server`,
`-copy`, `-paste`) and which keys from
`~/.piknik.toml` it uses.

## Use it for

```bash
# On the relay box (a tiny VPS, dedicated server, or any host with a public IP)
piknik -server &     # listens on Listen= from ~/.piknik.toml

# On any client (your laptop, a remote shell, a CI runner)
echo "hello" | piknik -copy
piknik -paste                       # → "hello"

# Transfer a file (or anything binary)
tar c logs/ | piknik -copy
# ... on the other machine:
piknik -paste | tar x

# Move a kubeconfig from the bastion to your laptop without scp
cat ~/.kube/config | piknik -copy
# laptop:
piknik -paste > ~/.kube/cluster-prod

# Multiple "slots" via -content-type — keep separate clipboards
echo "url-A" | piknik -copy -content-type url
echo "creds-B" | piknik -copy -content-type creds
piknik -paste -content-type creds   # → "creds-B"

# Move command output without leaving the terminal
kubectl get pods -o yaml | piknik -copy
# laptop / another shell:
piknik -paste | yq '.items[].metadata.name'

# Run as a launchd / systemd unit on the relay so it survives reboot
# (example unit file in the README at github.com/jedisct1/piknik)
```

The "clipboard" is a single buffer on the relay,
overwritten by each `-copy`, drained by `-paste`.
For history / multiple slots, run multiple relays
or use the `-content-type` flag to namespace.

## Why include it in a CLI catalog

1. **It collapses "transfer this small thing
   between two of my shells" from a 30-second
   `scp` ceremony to a one-line pipe.** No
   filename, no path negotiation, no key
   forwarding, no "wait, what's the bastion's IP
   again". For SREs, anyone hopping between cloud
   shells, anyone whose laptop and dev VM are on
   different networks, this is the missing
   primitive.
2. **The crypto is end-to-end and keyed off
   pre-shared secrets.** The relay sees only
   ciphertext + HMAC; it can be a third-party VPS
   you don't fully trust without leaking
   clipboard contents. Built by `jedisct1` (also
   the author of libsodium and dnscrypt), so the
   defaults are sane (XChaCha20-Poly1305-style
   AEAD via libsodium primitives, HMAC-SHA-512
   for routing).
3. **Single static Go binary on every relevant
   platform.** Linux x86_64 / arm / arm64,
   macOS arm64 + Intel, FreeBSD, OpenBSD, NetBSD,
   DragonflyBSD, Windows x86_64 + arm64. The
   release tarball page lists 14 OS / arch
   combinations. Drop into a container, an
   embedded device, a CI runner — works.

For an LLM-CLI workflow, `piknik` is the missing
"share this prompt / output between my laptop and
my GPU box" link: pipe the model's response on the
GPU host into `piknik -copy`, then `piknik -paste`
on the laptop where you're editing the document
the response feeds into. No file syncing, no
shared filesystem.

## Vs Already Cataloged

- **Vs [`magic-wormhole`](../magic-wormhole/) /
  [`croc`](../croc/):** different lifetime model —
  `wormhole` / `croc` are *one-shot* human-to-human
  transfers using an ephemeral phrase ("7-crossover-
  clockwork"). `piknik` is a *persistent* shared
  clipboard between *your own* machines using a
  long-lived shared key. Use wormhole / croc for
  "send this file to my coworker once"; use
  piknik for "I work across 5 machines and want
  them to share a clipboard all day".
- **Vs [`wl-clipboard`](../wl-clipboard/) /
  [`clipse`](../clipse/) / `pbcopy` / `xclip`:**
  orthogonal scope — those are *local* clipboard
  bridges, scoped to one machine's display server.
  `piknik` is *cross-machine*. The natural pairing
  is `wl-paste | piknik -copy` to push the local
  clipboard to the network, and `piknik -paste |
  wl-copy` to pull the network clipboard onto the
  local one — this is the canonical recipe in the
  upstream README.
- **Vs `scp` / `rsync` / [`rclone`](../rclone/):**
  different ergonomics — `scp` requires SSH access
  *from one endpoint to the other*, which often
  means reverse tunnels, jump hosts, or VPN
  permits between the two boxes. `piknik` only
  requires both endpoints can reach the relay,
  which is a much weaker connectivity assumption.
  scp / rsync win on file-tree fidelity; piknik
  wins on "I just want bytes, now".
- **Vs `nc` / `socat`:** lower level — `nc -l` +
  `nc host port` is the netcat way, but you have
  to coordinate ports, the channel is plaintext,
  and one side must be reachable from the other.
  piknik adds: encryption, authentication,
  buffering on the relay, no direct connectivity
  needed between endpoints.

## Caveats

- **You must run a relay.** Either a $3 VPS, a
  home server with a public IP, or — for
  same-LAN use — any always-on machine. There is
  no public hosted relay (deliberately: the relay
  trusts no client, and clients trust no relay,
  but you still need *some* relay process
  running).
- **The relay holds one buffer at a time.** A
  fresh `-copy` overwrites whatever was there;
  `-paste` does not pop. Two clients copying
  simultaneously will race. Use
  `-content-type SLOT` for namespacing if you
  need parallel channels.
- **No history / no audit log on the relay** —
  this is a privacy feature, not a bug. If you
  need an audit trail, log on the *clients*; the
  relay is intentionally amnesiac.
- **Pre-shared keys must reach every endpoint via
  some out-of-band channel** (1Password, Vault,
  ansible-vault, copy/paste over an existing SSH
  session). `piknik -genkeys` produces a
  ready-to-distribute TOML config; the
  bootstrapping is the only real friction.
- **HTTPS recommended for the relay endpoint**
  even though the payload itself is end-to-end
  encrypted — TLS protects the HMAC routing
  metadata and prevents trivial DoS / replay
  observation. Put the relay behind nginx /
  Caddy with a Let's Encrypt cert.
- **The LICENSE file's text is the ISC license**
  (the file header reads "ISC LICENSE"), but
  GitHub's license detector classifies the
  identical wording as **BSD-2-Clause**. Both are
  permissive, OSI-approved, and effectively
  equivalent (functionally a slimmed-down BSD).
  Safe to redistribute the binary inside a
  proprietary stack with attribution.
